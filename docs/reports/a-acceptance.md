## 首次发现的问题（现已修正）

### P2：合并器没有校验合并结果的全局约束

位置：`src/fgir/annotations.py`，`merge_annotations`，第180–184行。

复现：从同一份100条工作文件复制两个导出；第一份只把 `fine_001` 文本改成一个新的句子，第二份只把 `fine_002` 改成同一个句子。两份导出各自通过 `validate_annotations`，不存在同一 query_id 的编辑冲突。`merge_annotations` 返回成功并发布输出；再次校验输出则报 `duplicate fine-grained query text ... fine_002`。

影响：正常的多人独立修改可以形成无效交付文件，合并命令却报告成功。后续冻结会拒绝，所以尚未造成正式指标污染，但会在交接后才暴露问题。

修复要求：在创建输出目录之前，对 `merged` 调用完整的 `validate_queries(..., fine_grained=True)`。增加两份各自合法、合并后文本重复的回归用例，要求拒绝且不发布目录。

### P2：冷启动统计丢失原始阶段，混合不同测量量

位置：`src/fgir/analysis.py`，`summarize_latency`，第71–74行。

复现：同一设备、图库、K、批大小和缓存状态下，输入三条 `cold_start=true` 测量，阶段分别为 `text_encoding`、`vector_sort`、`end_to_end`，耗时为100、5、110 ms。工具把三者全部改为 `stage=cold_start`，输出一个组，样本数3、p50=100 ms、p95=109 ms。

影响：编码、排序与端到端不是同一种测量量，三者的混合分位数没有可用于性能报告的含义。D 按阶段记录首次查询时会触发。

修复要求：保留原始 stage，将冷启动状态作为额外分组维度；或者显式限制冷启动记录只允许某一种明确阶段。添加不同冷启动阶段不被合并的回归用例，并同步输出契约。
